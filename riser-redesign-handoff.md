## What's explicitly NOT done — the next pass

### 1. Tab restructuring (the reason this branch has no PR yet)

**The problem, from the PRD's own framing:** `docs/prd/Riser-PRD.md` explicitly calls the risk-triage ledger (Journey 2) "the core value and the centerpiece of the demo," and describes the target user (a property manager) as needing to see portfolio risk "at a glance." But the current page layout puts the ledger at the _very bottom_ — a user has to scroll past the header, an error banner, the Building Lookup form, the Add Building/Add Device forms, and the full Buildings list before ever reaching it. For the common case — a manager checking status, not onboarding a new building that day — this is backwards.

**The plan, agreed with Karl:** split the page into two tabs instead of one long scroll:

- **"Ledger" tab** (new default landing tab): the `ExecutiveSummaryBand` stat tiles, the `NarrationPanel` AI briefing, and the existing Ledger/Timeline sub-view (the current tab pair becomes nested inside this, or gets flattened — use judgment on the cleanest structure once you're looking at the real component tree).
- **"Manage Portfolio" tab** (new): `AddressLookupForm`, the `BuildingForm`/`ElevatorForm` pair, and `BuildingList`.

**One thing to watch:** `docs/prd/Riser-PRD.md` §3 Journey 1 has a P1 requirement that a first-time user (empty portfolio) sees a polished empty state pointing to the address-lookup path as the fast start. `LedgerPage`'s existing `EmptyState` component (check `frontend/src/components/EmptyState.tsx`) already has this messaging plus a "Try sample data" button — if the Ledger tab is now the default landing view and it's empty on first load, make sure that empty state's copy/CTA still makes sense pointing at a _different tab_ now (e.g., "Add your first building" as a link/button that switches to the Manage Portfolio tab, not just prose assuming the lookup form is already visible on the same screen).

**Implementation notes:**

- `App.tsx` already has a working two-tab pattern (`Ledger`/`Timeline`, `role="tablist"`, `aria-selected`, conditional mounting so only the active tab's content renders) — read that code and reuse the exact same pattern for the new top-level Ledger/Manage-Portfolio split, don't invent a new tab mechanism. You'll likely end up with tabs nested inside tabs (Ledger tab → Ledger/Timeline sub-tabs) or a flattened three-way tab row (Ledger / Timeline / Manage Portfolio) — either is defensible; pick based on what reads cleanest once you see it rendered, and check with Karl if genuinely unsure.
- This will touch `App.tsx`/`App.module.css` significantly — re-run the full verification suite (`npm run lint && npm run typecheck && npm run format:check && npm run test:coverage` from `frontend/`) and re-check `App.test.tsx` carefully, since it currently asserts a lot about what's visible/mounted at once.
- Consider whether `frontend/e2e/` specs need updates too — several navigate straight to interacting with the ledger or the forms assuming they're both on-screen simultaneously; check `frontend/e2e/ledger.spec.ts` and `frontend/e2e/keyboard-accessibility.spec.ts` for this assumption once the tabs exist.

### 2. Other loose ends worth knowing about

- **`frontend/e2e/ledger.spec.ts` has a pre-existing (not-mine, not from this session's work) no-op assertion**: the "edit an elevator" test uses `page.getByRole("row").filter({ hasText: /^EL-1$/ })` to assert a row is gone after a rename — Playwright's `hasText` regex matches against the row's _entire_ text content, so an anchored `^...$` pattern against a whole `<tr>` essentially never matches regardless of whether the row exists.
